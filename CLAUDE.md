# CLAUDE.md — Tricot

Ce fichier est la référence de travail pour tout agent (Claude ou humain) qui intervient sur ce dépôt.

## Résumé de l'application

"Tricot" est une PWA personnelle et privée (un seul utilisateur, pas de compte, pas de paiement, aucune fonctionnalité sociale) pour centraliser :

- la gestion des projets de tricot/crochet (statut, patron associé, laine, notes, progression) ;
- des compteurs de rangs multiples par projet, plus un compteur autonome ;
- le suivi du temps de travail par session ;
- une bibliothèque de patrons PDF avec visionneuse intégrée ;
- des guides de patrons structurés (manuels, puis analysés par IA plus tard) avec mode tricot ;
- un stock de laine avec suivi de consommation et vérification de disponibilité ;
- des statistiques personnelles.

Cible principale : iPhone/iPad (Safari, installée sur l'écran d'accueil), utilisable d'une seule main pendant le tricot. Fonctionne aussi sur ordinateur. Offline-first, aucun backend pour l'instant. Hébergée sur GitHub Pages (site statique).

Le nom de l'application est centralisé dans `src/config/appInfo.ts` (`APP_NAME`) — c'est la seule chose à changer pour renommer l'app. Le manifest PWA garde sa propre copie de ce nom dans `vite.config.ts` (contrainte technique : le manifest est généré côté build, avant que le code applicatif ne soit exécuté) ; les deux doivent rester synchronisés, un commentaire le rappelle à chaque endroit.

Le cahier des charges complet est dans `docs/SPEC`. C'est la référence fonctionnelle, mais on n'implémente jamais tout d'un coup : on avance étape par étape (voir Feuille de route ci-dessous), une seule à la fois, validée par l'utilisateur avant de passer à la suivante.

## Stack

- Vite + React + TypeScript (mode strict)
- Dexie (IndexedDB) pour les données, via un module d'accès unique (`src/data`)
- vite-plugin-pwa (manifest + service worker)
- React Router (`createHashRouter`, HashRouter — nécessaire sur GitHub Pages, qui ne sait pas réécrire les routes côté serveur)
- CSS Modules (pas de librairie UI), système de tokens dans `src/styles/tokens.css`
- lucide-react pour les icônes (+ `YarnBallIcon`, une icône perso pour l'onglet Laine)
- Polices variables installées en local (`@fontsource-variable/outfit`, `@fontsource-variable/dm-sans`), jamais de CDN
- `pdfjs-dist` (étape 4) pour la bibliothèque de patrons et sa visionneuse, isolé dans `src/pdf/`, chargé uniquement à la demande (voir CLAUDE.md "pdf.js")
- `@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/utilities` (étape 5a) pour le glisser-déposer tactile dans l'éditeur de guide, utilisés uniquement dans `src/components/guides/editor/` (voir "Décisions d'interface (étape 5a)") ; la route de l'éditeur est chargée en import dynamique pour que ce code ne rejoigne jamais le bundle principal.
- `jszip` (étape 7) pour le fichier de sauvegarde `.zip`, chargé uniquement à la demande (`import()` dans `src/data/backup/`, son propre chunk, jamais dans le bundle principal)
- Interface en français, code/variables/commentaires en anglais

Ne pas ajouter d'autre dépendance sans validation explicite de l'utilisateur. Si une alternative semble meilleure, la justifier en 2 lignes avant de l'utiliser.

## Conventions de code

- TypeScript strict partout (`strict: true` dans les deux tsconfig). Pas de `any` non justifié.
- Toute entité persistée a un `id` (UUID via `crypto.randomUUID()`, voir `src/data/id.ts`), un `createdAt` et un `updatedAt` (ISO string). Voir `BaseEntity` dans `src/data/types.ts`.
- Aucun appel Dexie direct dans les composants : tout passe par `src/data` (le module unique d'accès aux données) ou par un hook construit dessus (ex. `src/hooks/useSettings.ts`, basé sur `Dexie.liveQuery`).
- Schéma Dexie versionné : ne jamais modifier un `.version(n)` déjà publié. Toute évolution de schéma ajoute un nouveau `.version(n + 1)` avec `.upgrade()` si besoin d'une migration de données. Voir le commentaire en tête de `src/data/db.ts`.
- Composants et fichiers CSS associés en `Composant.module.css` à côté du composant.
- Pas de commentaire qui décrit ce que fait le code ; seulement le pourquoi quand ce n'est pas évident (contrainte cachée, choix technique non intuitif).

## Principes de design

- **Offline-first** : toute fonctionnalité listée à la section 25 du cahier des charges doit fonctionner sans réseau, y compris juste après l'installation. Les polices sont installées en local et précachées par le service worker (`globPatterns` inclut `woff2` dans `vite.config.ts`) pour la même raison.
- **Mobile-first** : on conçoit d'abord pour iPhone, puis on adapte à iPad/ordinateur (navigation latérale plutôt que pilule flottante au-delà de 768px, voir `src/components/layout/FloatingTabBar`).
- **Utilisable d'une seule main** : les actions fréquentes (compteurs, navigation principale) doivent être atteignables par le pouce, en bas d'écran.
- **Gros boutons tactiles** : zone tactile minimale 48px (`--tap-min`), boutons de comptage 72px minimum (`--counter-btn-min`).
- **Safe areas iOS** : toujours respecter `env(safe-area-inset-*)` (variables `--safe-top/bottom/left/right` définies dans `src/styles/tokens.css`) sur les éléments collés aux bords de l'écran (header, barre flottante, contenu plein écran), y compris en paysage sur iPad (safe areas gauche/droite).
- **Thème clair uniquement.** Ne pas ajouter de mode sombre sans demande explicite de l'utilisateur : pas de `prefers-color-scheme: dark`, pas de réglage de thème, pas de valeurs sombres dans les tokens. `color-scheme: light` et les meta iOS/manifest sont alignés sur le fond crème (`#FCF8F3`).
- Design 100 % original, style doux/chaleureux/artisanal inspiré du tricot (fond crème, framboise en couleur principale, cartes très arrondies, séparations ondulées, motif de rayures) : le cahier des charges s'inspire des fonctionnalités d'une app existante, mais on ne reprend ni son nom, ni son logo, ni son design visuel.

## Système de design

- Tous les tokens (couleurs, rayons, espacements, tailles de texte, ombres, transitions, zones tactiles, safe areas) vivent dans `src/styles/tokens.css`, seul fichier de ce type. Aucune valeur en dur dans les composants : toujours passer par un token.
- Motif de rayures (signature visuelle, rappel du tricot) : utilitaire CSS dans `src/styles/patterns.module.css` (`.stripes` + une classe par couleur de projet), utilisé par `StripedProgressBar` et à réutiliser pour les couvertures de projet par défaut.
- Composants de base réutilisables dans `src/components/ui` : `Button`, `IconButton`, `Card`, `HeroCard`, `Pill`, `StatTile`, `ProgressRing` (accepte `color`/`trackColor` pour une couleur personnalisée), `StripedProgressBar`, `WaveDivider`, `PageHeader`, `SectionTitle`, `Sheet` (feuille modale générique), `ConfirmDialog` (confirmation obligatoire, basé sur `Sheet`), `SquareTile` (raccourci carré type icône, pour la section "Outils" de l'accueil). Aucun ne contient de logique métier.
- Couleur d'un projet appliquée à son interface via `src/components/projects/colorMeta.ts` (`projectColorVar`, `projectColorSoftVar`, `projectGradient`) : en-tête de la fiche projet, anneau de progression, bouton "Continuer", encadré des cartes dans la liste.
- Navigation : `FloatingTabBar` (`src/components/layout`) est un seul composant à deux rendus pilotés par media query — pilule flottante sur mobile, navigation latérale à partir de 768px. Les Réglages restent accessibles via l'icône `Settings` dans `AppHeader`, pas dans la barre de navigation.
- Icônes : lucide-react (trait 1.75, tailles 20/24/28), wrappées dans `src/components/icons/lucide.tsx` pour appliquer le trait uniformément. `YarnBallIcon` (`src/components/icons/YarnBallIcon.tsx`) est une icône SVG perso pour l'onglet Laine. Le `Logo` (`src/components/Logo.tsx`, lit `APP_NAME`) est une pelote framboise aux fils crème en diagonale avec un brin de laine ; la même géométrie (pelote crème, fils framboise, sur fond framboise `#C2416B`) est la source de `public/favicon.svg` et des PNG de `public/icons/` (192, 512, maskable avec marge de sécurité, apple-touch) — à garder synchronisés si le logo change.
- Écran de chargement : crème avec logo et nom, en deux couches. (1) Un écran de démarrage statique est écrit directement dans `<div id="root">` de `index.html` (CSS et SVG en ligne, donc affiché avant tout bundle) et disparaît au premier rendu de React ; il copie le logo de `Logo.tsx` et le nom `APP_NAME` en dur, comme le `<title>`. Il s'affiche donc dans la police système, Outfit n'étant pas encore chargée. (2) Les écrans de lancement iOS (`public/splash/*.png`, un par taille d'iPhone/iPad en portrait, déclarés par des `<link rel="apple-touch-startup-image">` dans `index.html`) sont générés par `scripts/generate-splash.mjs` (hors build : demande playwright et Chromium) ; ils sont exclus du précache (`globIgnores`) car c'est iOS qui les récupère. iOS les met en cache à l'installation : réinstaller l'app pour voir un changement. Pas de variante paysage.
- Page `/#/styleguide` (`src/pages/StyleguidePage.tsx`) : référence visuelle vivante — palette, échelles, typographie, icônes, composants dans leurs variantes, couleurs de projet avec rayures, et un exemple de page type. À tenir à jour à chaque ajout de token ou de composant.
- Couleurs de projet (prune, pervenche, terracotta, pêche, rouge, rose) : chacune a une variante `-soft` dérivée via `color-mix()` dans les tokens. Le doré et le sage ne servent jamais pour du petit texte (contraste insuffisant sur fond crème) : uniquement fonds/icônes/barres/badges.
- Croquis de référence dans `docs/design/sketches/` (compteur, accueil, fiche projet), pour les étapes 1 et 6 :
  - Compteur : gros boutons dans la moitié basse de l'écran (zone du pouce), +1 nettement le plus grand, -1 plus petit et à l'écart de +1.
  - Accueil et fiche projet : même anneau de progression (`ProgressRing`) et même bouton d'action principal.

## Règles de travail

- **Une étape à la fois.** Ne jamais implémenter une fonctionnalité qui appartient à une étape future de la feuille de route, même si elle semble facile ou liée.
- Avant de commencer une étape, s'assurer d'avoir bien compris son périmètre exact ; poser des questions courtes en cas d'ambiguïté plutôt que de deviner un scope plus large.
- Commits petits et clairs, un sujet cohérent par commit (pas de "gros commit fourre-tout").
- À la fin de chaque étape : lancer typecheck, lint et build, corriger les erreurs, puis s'arrêter et attendre la validation de l'utilisateur avant de continuer.
- Ne pas committer de contenu personnel : PDF de patrons, sauvegardes, photos, clés API. Voir `.gitignore`.

## Fonctionnalités explicitement exclues

D'après la section « Confidentialité » du cahier des charges (l'app est mono-utilisateur, aucune fonctionnalité sociale n'est nécessaire), ne jamais implémenter :

- profils publics ;
- followers / abonnés ;
- likes ;
- commentaires ;
- fil d'actualité ;
- messagerie ;
- partage communautaire / publication sociale intégrée.

Par ailleurs, pas de compte utilisateur ni de système de paiement/abonnement (section 1). Les patrons importés restent privés et ne doivent jamais servir à entraîner un modèle d'IA (section 32).

## Règles de calcul de la laine (étape 3a)

Tout est calculé en pelotes en interne (`src/data/yarnMath.ts`, fonctions pures et testées), converties via `metersPerSkein`/`gramsPerSkein` ; `toSkeins`/`fromSkeins` renvoient `null` quand la conversion est impossible (figure par pelote manquante).

- `computeYarnStockSummary(yarn, usages, projectYarns, projects)` : initiale = `skeinCount` ; consommée = somme de tous les `yarnUsages` du fil (tous projets confondus, y compris `projectId: null`) ; restante = initiale − consommée (`null` si négative → afficher "stock dépassé", jamais une valeur négative) ; réservée = somme, sur les projets liés au statut "à faire"/"en cours"/"en pause", de `max(prévu − consommé par ce projet, 0)` (un projet "terminé" ne réserve plus rien) ; disponible = restante − réservée (peut être négatif : signale une réservation supérieure à ce qu'il reste, distinct du cas "stock dépassé").
- `checkProjectYarnAvailability(link, yarn, usages, projectYarns, projects)` : besoin = prévu − déjà consommé par ce projet ; stock = restante − réservée par les **autres** projets ; résultat `'ok' | 'missing' | 'unknown'` (`'unknown'` si la conversion est impossible — message "Vérification impossible : renseigne le poids ou le métrage par pelote du fil").
- `computeProjectYarnLinkProgress` : consommé/prévu d'un lien projet-fil, pour la StripedProgressBar et le pourcentage.
- `computeYarnStockBarSegments(stock)` : traduit un `YarnStockSummary` en trois largeurs (0–1, somme ≤ 1) pour la barre segmentée de la fiche fil (`YarnStockBar`) — voir "Décisions d'interface (étape 3a)".
- `computeProjectYarnSummary(projectId)` (`src/data/yarnsRepository.ts`) : laine prévue/consommée/restante/pourcentage d'un projet tous fils confondus (en pelotes, seule unité qui peut les combiner) — exposée pour l'étape 6.
- Recherche/tri/filtres : fonction pure `filterAndSortYarns` (`src/data/yarnSearch.ts`), testée séparément des écrans.

## Règles de la licence Ravelry (résumé)

L'API Ravelry est utilisée uniquement en lecture, avec les identifiants personnels en lecture seule de l'utilisateur (jamais une clé applicative partagée). Règles appliquées dans le code :

- Aucune affiliation suggérée : mention "Non affilié à Ravelry" dans les Réglages et près de la recherche, pas de logo ni de couleur de marque Ravelry, nom de l'app inchangé.
- Seul du texte technique est conservé (nom, marque, épaisseur, métrage, poids, composition, identifiant, lien) — jamais de photo, description ou avis du catalogue.
- Aucune donnée Ravelry n'est mise en cache : le service worker exclut explicitement `api.ravelry.com` (`src/ravelry/serviceWorkerRule.ts`, stratégie NetworkOnly, vérifié par `serviceWorkerRule.test.ts` et par une inspection du `sw.js` généré).
- La recherche ne se déclenche qu'à la demande explicite de l'utilisateur (bouton "Rechercher"), jamais en arrière-plan ni au chargement.
- Le repo ne contient aucune donnée réelle de Ravelry : tous les tests utilisent des fils et identifiants inventés.
- L'utilisateur peut tout supprimer à la demande : "Effacer mes identifiants" (Réglages) et "Supprimer les données Ravelry" (purge des champs encore issus du catalogue sur chaque fil, voir `purgeRavelryData`).

## Isolation du module Ravelry

Tout le code vit dans `src/ravelry/` (client HTTP, mapping tolérant, limiteur de débit, composants, pages), avec un point d'entrée unique `src/ravelry/index.ts`. Pour retirer complètement la fonctionnalité :

1. Supprimer le dossier `src/ravelry/`.
2. Retirer l'import et le rendu de `RavelrySettingsSection` dans `src/pages/SettingsPage.tsx`.
3. Retirer le bouton "Rechercher dans le catalogue", le message vers les Réglages, la pill "Prérempli…" et `<RavelrySearchSheet>` dans `src/pages/YarnFormPage.tsx`, ainsi que les états/handlers `catalog*`/`ravelry*` qui leur sont propres.
4. Retirer `<RavelryCatalogPill>` dans `src/pages/YarnDetailPage.tsx`.
5. Retirer la route `/diagnostic-ravelry` et son import dans `src/app/router.tsx`.
6. Retirer l'import de `RAVELRY_RUNTIME_CACHING_RULE` et l'option `runtimeCaching` dans `vite.config.ts`.

Les champs `ravelryYarnId`/`catalogSource`/`ravelryPermalink`/`catalogFields`/`catalogFetchedAt` sur `yarns` et `ravelryEnabled`/`ravelryUsername`/`ravelryPassword` sur `settings` peuvent rester dans le schéma (jamais renseignés, sans effet) : un schéma Dexie déjà publié ne se modifie jamais rétroactivement (voir la convention de migration en tête de `src/data/db.ts`).

## Suppression et laine

- Supprimer un fil (`deleteYarn`) : cascade sur ses `projectYarns`, ses `yarnUsages` et sa photo.
- Supprimer un projet (`deleteProject(id, keepYarnUsage = true)`) : ses `projectYarns` sont toujours supprimés (un prévu n'a pas de sens sans projet) ; `keepYarnUsage` (case à cocher "Conserver la laine consommée dans le stock" dans `ProjectFormPage`, cochée par défaut) décide du sort de ses `yarnUsages` — `true` les réattribue à `projectId: null` (la laine reste déduite du stock), `false` les supprime (la laine est rendue au stock).

Un seul état par couple (patternId, projectId) — recherché par l'index `patternId` seul et filtré en JS pour le cas `projectId: null`, IndexedDB n'indexant jamais les valeurs `null` (même contrainte que `counters.projectId`/`sessions.projectId`, voir plus haut).
- `projects.lastWorkTab` (`'pattern' | 'counter' | 'guide' | null`) : dernier onglet actif de la vue de travail (étape 4), lu par l'étape 6 pour "Reprendre" et par le bouton "Continuer" de la fiche projet.
- Import atomique (`importPattern`, `src/data/patternsRepository.ts`) : métadonnées, fichier et couverture écrits dans une seule transaction Dexie — un échec (dont `QuotaExceededError`) fait annuler toute la transaction par IndexedDB, rien n'est jamais écrit partiellement.
- Remplacement de version (`replacePatternFile`) : nouveau fichier, `fileVersion + 1`, nouvelles métadonnées de page/taille/hash, couverture auto régénérée si elle l'était encore ; métadonnées, tags et liens projet conservés ; chaque `patternViewStates.page` de ce patron est ramené dans `[1, nouveau pageCount]`.
- Suppression d'un patron (`deletePattern`) : cascade sur son fichier, sa couverture, ses `projectPatterns` et ses `patternViewStates`. Suppression d'un projet (`deleteProject`) : supprime ses `projectPatterns` et `patternViewStates`, ne touche jamais au patron lui-même (même logique que pour la laine).
- Lecture et rendu du PDF isolés dans `src/pdf/` (`pdfjs.ts` charge pdf.js et son worker en différé via `import()`, jamais depuis le chemin statique — voir "pdf.js" plus bas ; `extractPdfMetadata.ts` lit le nombre de pages/le titre et rend la couverture automatique ; `viewerMath.ts` regroupe les fonctions pures testées de bornage page/zoom et de budget mémoire de rendu, utilisées par `PdfViewerCore`).

## pdf.js

- `pdfjs-dist` (v6, dépendance unique ajoutée à l'étape 4) n'a plus qu'un seul build ESM moderne — l'ancien build "legacy" pour navigateurs pré-2021 n'existe plus dans cette version, donc le choix ne s'est pas posé : c'est ce build qui est utilisé, et il convient très bien puisque l'app ne tourne que sur Safari iOS/iPadOS récent (installée sur l'écran d'accueil).
- `src/pdf/pdfjs.ts` charge la bibliothèque et son worker (`pdfjs-dist/build/pdf.worker.min.mjs?url`, importé dynamiquement) uniquement à la demande : ni la bibliothèque de patrons ni la fiche projet ne l'importent statiquement, seuls l'import d'un PDF et la visionneuse le font, tous deux déjà derrière un `import()`. Résultat vérifié au build : le chunk principal de l'app ne contient pas pdf.js, qui forme ses propres chunks (bibliothèque ~430 Ko, worker ~1,3 Mo) chargés uniquement à l'ouverture d'un PDF.
- Polices standard non intégrées : `standardFontDataUrl` pointe vers `public/pdf/standard-fonts/` (copié depuis `node_modules/pdfjs-dist/standard_fonts` par `scripts/copy-pdfjs-assets.mjs`, lancé avant `dev`/`build` — jamais commité, voir `.gitignore`) pour un rendu correct même hors ligne. Les CMaps (`node_modules/pdfjs-dist/cmaps`, ~1,7 Mo, essentiellement des encodages CJK) ne sont volontairement pas embarquées : les patrons de cette app sont en français/anglais, le poids ne se justifie pas.
- Précache du service worker : `vite.config.ts` ajoute `mjs`/`pfb`/`ttf` à `globPatterns` (le worker pdf.js garde l'extension `.mjs`, les polices standard `.pfb`/`.ttf`) et relève `maximumFileSizeToCacheInBytes` à 4 Mo (le worker minifié pèse à lui seul ~1,3 Mo, au-dessus de la limite par défaut de workbox). Aucune requête réseau n'est faite par la bibliothèque ni la visionneuse : ni `cMapUrl` (CMaps non embarquées, voir ci-dessus) ni aucun appel à `api.ravelry.com` ou équivalent.
- `extractPdfMetadata` clone toujours le buffer avant de le passer à `pdfjs.getDocument({ data })` (`data.slice(0)`) : pdf.js transfère (détache) l'`ArrayBuffer` qu'on lui donne vers son worker, alors que l'appelant (import, remplacement de fichier) réutilise ce même buffer juste après pour le hasher et l'enregistrer comme fichier du patron — sans ce clone, le fichier stocké se retrouvait vide.
- Pas de recherche de texte dans la visionneuse (retirée après l'étape 4 : `page.getTextContent()` existe dans pdf.js mais construire un index par page à la demande sans expérience solide de surbrillance n'apportait pas assez pour sa complexité). À reconsidérer plus tard si le besoin se confirme.

## Extraction heuristique (étape 4, post-lancement)

À l'import (et lors d'un remplacement de fichier), `extractPdfMetadata` (`src/pdf/extractPdfMetadata.ts`) tente de préremplir nom/créatrice/matériel/couverture à partir du contenu réel du PDF plutôt que de ses seules métadonnées d'enregistrement — sans IA, uniquement de la typographie et une liste de tournures fixes bilingue (français/anglais). C'est un préremplissage à vérifier, jamais une vérité : tous les champs concernés restent modifiables avant "Enregistrer" (import d'un seul fichier) ou après coup depuis la fiche du patron (import multiple, sans formulaire intermédiaire).

- **Regroupement en lignes** (`groupTextIntoLines`) : d'abord par proximité verticale réelle des fragments de texte (`transform[5]`, la position Y), le flag `hasEOL` de pdf.js n'étant qu'un point de coupure secondaire — se fier uniquement à `hasEOL` fusionnait toute une page en une seule "ligne" géante sur les PDF où chaque bloc de texte est positionné indépendamment (mise en page Canva/InDesign/Affinity plutôt que texte au fil), ce que les filtres de longueur du titre/de la créatrice rejetaient silencieusement.
- **Titre** (`guessTitleFromLines`, `src/pdf/patternTextHeuristics.ts`) : la ligne de texte à la plus grande taille de police, cherchée sur la première page puis, si rien de plausible, les pages suivantes (jusqu'à 5) — une couverture entièrement graphique est souvent suivie d'une page de titre en texte réel. La métadonnée `Title` du PDF reflète souvent le nom du fichier, pas celui du patron, donc elle ne sert plus que de tout dernier repli. Fonctionne pareil en français et en anglais : le signal est la taille de police, pas des mots-clés.
- **Créatrice/créateur** (`guessCreatorFromLines`) : même parcours multi-pages, reconnaît une ligne commençant par une tournure fixe ("Par…", "Conçu par…", "Un modèle de…", "Designed by…", "Pattern by…"…) — ancrée en début de ligne pour ne jamais matcher au milieu d'une phrase. Repli sur la métadonnée `Author` si rien ne correspond. Préremplit le champ "Source".
- **Matériel** (`findMaterialLines`) : ne retient une ligne que si elle contient À LA FOIS un mot-outil (aiguille/needle/crochet/hook/DPN) ET une mesure (mm/cm/in/pouces) — les deux seuls en isolation sont trop fréquents dans un texte d'instructions ordinaire pour être fiables. Scanne les 5 premières pages, dédoublonné, plafonné à 10 lignes. Préremplit le champ dédié `patterns.materials` (une ligne brute détectée par ligne du champ, jamais reformulées) — jamais les Notes, qui restent un champ libre séparé.
- **Couverture rognée** (`cropToCoverImage`, `src/pdf/extractCoverImage.ts`) : cherche la plus grande image intégrée dans la première page en rejouant sa liste d'opérateurs pdf.js (`getOperatorList`) et en suivant la matrice de transformation courante (`save`/`restore`/`cm`, modèle standard PDF où une image est peinte dans le carré unité sous la CTM) ; convertit son rectangle en espace page vers l'espace pixel du canvas déjà rendu via `viewport.transform` et `Util.axialAlignedBoundingBox`, puis rogne. Repli silencieux sur la page entière (comportement précédent) si aucune image trouvée, si le rectangle est disproportionné (< 8 % ou > 97 % de la page) ou en cas d'erreur — les PDF réels sont trop variés pour risquer une couverture absurde.
- Toute cette logique est dans `src/pdf/`, jamais importée statiquement ailleurs (voir "pdf.js" ci-dessus) : elle ne s'exécute qu'à l'import/au remplacement, comme le reste du module.

## Modèle de données (étape 5a — guides de patron)

- Format du guide : arbre typé JSON pur (`GuideContent`, `src/data/guideModel.ts`) — Pièces > Sections > Blocs > Rangs, plus une opération de montage et une de finition par pièce. Décrit en détail dans `docs/Guidespatrons.md` (section "Format JSON" pour la forme exacte, avec un exemple inventé). Aucune classe, `Date` ni `Map` dans ce format : uniquement objets/tableaux/texte/nombres/booléens, pour rester sérialisable tel quel (export étape 7, génération IA étape 9).
- **Ids stables** : chaque nœud garde le même `id` tant qu'il existe — le modifier ou le déplacer ne le change jamais, seule une duplication (`duplicateNode`) mint de nouveaux ids pour le sous-arbre dupliqué. Indispensable : l'étape 5b accrochera la progression à ces ids, et l'étape 9 devra produire des guides avec des ids stables dès la génération.
- **La progression ne va jamais dans l'arbre.** Un guide est un modèle réutilisable, associable à plusieurs projets (`projectGuides`) — la position de lecture pour un projet donné vit dans une table séparée depuis l'étape 5b (`guideProgress`, indexée par `[projectId+guideId]`, jamais par id de nœud), jamais dans `guideContents`. C'est aussi ce qui distingue ce format du brouillon pré-implémentation qui existait avant cette étape (retiré, voir historique git). Voir "Modèle de données (étape 5b — progression des guides)" pour le détail.
- Schéma Dexie en version 11 (`src/data/db.ts`) : v11 ajoute `guides` (métadonnées : name, craft, patternId nullable, sizeLabel, notes, lastEditedNodeId), `guideContents` (le `GuideContent`, table séparée pour que les listes restent rapides — id = guideId, même convention que `patternFiles`) et `projectGuides` (un lien par couple projet/guide, comme `projectPatterns`).
- Fonctions pures et testées dans `src/data/guideTree.ts` : lecture (`findNode`, `getParentAndIndex`, `computeNodeDepth`), édition immutable (`addPiece`/`addSection`/`addBlock`/`addRow`/`setOperation`, `updateNode`, `moveNode`, `duplicateNode`, `deleteNode`), règles (`canNest`, profondeur maximale `MAX_BLOCK_NESTING_DEPTH` = 4 niveaux de blocs, tout type confondu), statistiques (`countRows`/`computeGuideStats` — un bloc `measure`/`stitch_count` a une longueur variable, jamais estimée, seulement signalée), saisie (`parsePastedRows`), validation/réparation (`validateGuideContent`/`normalizeGuideContent`, l'étape 9 s'en servira pour fiabiliser la sortie d'un modèle d'IA) et migration (`migrateGuideContent`, identité pour la v1).
- Couche de données dans `src/data/guidesRepository.ts` : `createGuide` (crée le guide et son contenu vide dans une seule transaction), `saveGuideContent` (écrit le contenu entier + `lastEditedNodeId`, utilisé par l'autosave de l'éditeur), `duplicateGuide` (copie complète, nouveaux ids sur tous les nœuds via `cloneGuideContentWithNewIds`, nom "Copie de ..."), `deleteGuide` (cascade sur le contenu et les liens projet), `linkGuideToProject`/`unlinkGuideFromProject` (un lien par couple, comme les patrons/la laine).
- Cascades mises à jour : supprimer un patron (`deletePattern`) ne supprime pas les guides qui le référençaient, il repasse simplement leur `patternId` à `null` (un guide reste un modèle utilisable sans patron) ; supprimer un projet (`deleteProject`) supprime ses `projectGuides` mais jamais les guides eux-mêmes (même logique que pour les patrons et la laine).
- Depuis l'étape 5b, le mode suivi lit cet arbre pour piloter la progression et appelle `recordActivity`/`startSession` (étape 2) avec `origin: 'guide'` et le `projectId` du projet en cours de suivi, exactement comme un compteur. L'étape 7 (export/sauvegarde, faite) inclut `guides`, `guideContents`, `projectGuides` **et `guideProgress`** dans la sauvegarde complète.

## Décisions d'interface (étape 5a)

- **Onglet Patrons** : sélecteur en pilule "Patrons | Guides" en haut (`PatternsPage`), qui bascule tout le contenu de la page (titre, recherche, grille) entre la bibliothèque de patrons existante et `GuidesLibraryView` (recherche par nom, cartes horizontales avec nom/patron lié/nombre de pièces et de rangs via `computeGuideStats`/projets liés, état vide "Crée ton premier guide pour suivre un patron étape par étape").
- **Création d'un guide** (`CreateGuideSheet`, réutilisée depuis la bibliothèque, la fiche projet et la fiche patron) : nom (obligatoire, préremplit depuis le nom du patron choisi tant que l'utilisateur n'a pas tapé le sien — uniquement à la création, jamais resynchronisé après si le lien change), type, patron lié (optionnel, recherche inline dans la bibliothèque), taille (texte libre optionnel). Peut être préremplie (`defaultCraft`/`defaultPatternId`) selon le point d'entrée.
- **Éditeur** (`GuideEditorPage`, route dédiée `/#/guides/:guideId`, chargée en import dynamique, sans `FloatingTabBar`) : vue arborescente Pièce > Section > Bloc > Rang, chaque niveau pliable indépendamment sauf un bloc `rows` (rien à y déplier, voir "Rangs" plus bas) — `TreeNodeHeader` affiche poignée de glisser-déposer (un simple point coloré, pas une icône à 6 points), une icône par catégorie (`iconPosition`, `'start'` par défaut juste après le point — `'end'`, juste avant le plier/déplier, comparée sur demande mais pas retenue), zone principale qui ouvre l'éditeur du nœud, puis à droite le plier/déplier de ce nœud (chevron, jamais à gauche : ça laissait moins de place à la zone de gauche point+icône+titre) et le menu "⋯". Deux traitements visuels distincts, jamais par profondeur d'imbrication (retour utilisateur après un premier essai en contour uniforme, qui rendait les blocs imbriqués illisibles) : Pièce et Section ont un **contour complet** dans la couleur de leur catégorie (`--color-guide-piece` = framboise/`--color-primary`, `--color-guide-section` dans `tokens.css`) ; un bloc, à n'importe quelle profondeur, a un **fond teinté** dans la couleur de son type (`--color-guide-*-soft`). L'indentation d'un nœud est une **marge sur sa propre boîte** (jamais un padding interne à la boîte, 20px par niveau — `INDENT_PX`, exporté par `TreeNodeHeader` et réutilisé tel quel par `BlockList`/`SectionCard`/`PieceCard` pour que les boutons "Ajouter…" restent alignés) : c'est ce qui fait que le contour/le fond rétrécit réellement avec la profondeur au lieu de courir sur toute la largeur sous un texte simplement décalé. Ligne de connexion façon organigramme (`SortableList`'s `connectorDepth`, en `--color-border`) à la fois pour la liste des sections d'une pièce et pour chaque liste de blocs (y compris imbriqués) — celle du "dernier" nœud du tronc n'est **jamais** déterminée par `:last-child` (un bug : la liste des sections n'est pas le dernier élément visuel de la pièce, montage/finition suivent) mais par une classe explicite (`connectorItemLast`, portée par `connectorTerminates` sur `SortableList` et par `ConnectorItem` pour un nœud non-triable comme montage/finition) : le tronc de la pièce part du montage, traverse ses sections (`connectorTerminates={false}` sur leur liste : elle ne termine jamais le tronc) et s'arrête à la finition, qui est toujours le vrai dernier nœud puisqu'elle est toujours affichée. Une seule pilule "Tout déplier"/"Tout plier" (bascule selon l'état courant, calculé une fois par rendu), alignée à droite de la barre d'outils sous l'en-tête pour laisser la place à gauche. L'en-tête porte retour, nom, indicateur "Enregistré"/"Enregistrement…"/"Échec de l'enregistrement" (sur sa propre ligne, sous le nom, pour ne jamais tronquer un nom un peu long), Annuler/Rétablir et le menu du guide (modifier nom/type/patron/taille en une seule feuille, dupliquer, supprimer avec confirmation listant les projets liés).
- **Panneaux d'édition plein écran** (`FullScreenPanel`, retour utilisateur après test réel) : la pièce, la section et chaque type de bloc (texte, répétition, mesure, nombre de mailles) s'éditent dans un panneau plein écran qui glisse depuis la droite ("Fermer" à gauche, titre au centre — jamais "Annuler", déjà pris par le Annuler/Rétablir de l'en-tête), plutôt que dans la feuille du bas utilisée ailleurs dans l'app. Aucun champ n'a `autoFocus` : ouvrir un panneau ne déclenche jamais le clavier, seule une saisie volontaire le fait. Un vrai bouton "Enregistrer" applique le formulaire ; "Fermer" annule. Si le guide a un patron lié, un bouton dans l'en-tête (icône livre) ouvre ce patron en plein écran par-dessus le panneau (`PdfViewerCore`, `projectId: null`) ; le retour ramène exactement au même panneau, jamais démonté entre-temps. Montage et finition (icônes Play/Flag) sont visibles directement dans l'arbre, juste sous la pièce (montage) et juste après ses sections (finition) — retour utilisateur après un essai où ils ne vivaient que dans le panneau "Pièce" et n'apparaissaient donc plus au premier coup d'œil ; chacun ouvre son propre `OperationSheet` en plein écran, la fiche pièce elle-même ne contient plus que nom/type/notes.
- **Type de pièce/section** : en plus du nom libre, une pièce a un type optionnel dans une liste fermée (devant, dos, manche, corps, empiècement, col, capuche, poche, ceinture, ou "Autre" avec un champ libre) affiché en pilules dans son panneau d'édition ; une section a la même logique additive (côtes, corps, mise en forme, jacquard, encolure, épaules, ou "Autre"). Champ nommé `category` (jamais `type`) dans le modèle — voir `docs/Guidespatrons.md`.
- **Glisser-déposer** (`SortableList`/`DragHandle`, `@dnd-kit`) : un `DndContext` indépendant par liste (pièces d'un guide, sections d'une pièce, blocs d'une section ou d'un conteneur, rangs d'un bloc) puisqu'un nœud ne se déplace jamais hors de sa liste parente. Le glissé ne démarre que depuis la poignée (`touch-action: none`, capteur tactile à délai d'activation) pour ne jamais capturer un défilement ; Monter/Descendre dans le menu "⋯" offre le même résultat sans glisser.
- **Ajout d'un bloc** : feuille de choix du type (`BlockTypePickerSheet`, reste une feuille compacte du bas — contrairement aux panneaux d'édition, choisir un type n'est pas une saisie) filtrée par `canNest` pour ne jamais proposer un type qui dépasserait la profondeur maximale, chaque option bordée de la couleur de son type ; le bloc est créé avec des valeurs par défaut puis son panneau d'édition s'ouvre aussitôt (y compris `rows`, qui ouvre directement l'écran Rangs). Le bouton d'ajout à l'intérieur d'un bloc conteneur dit "Ajouter un bloc imbriqué" (icône dédiée), distinct du "Ajouter un bloc" d'une section : les deux créaient déjà des nœuds à des endroits différents (enfant du conteneur vs frère au niveau de la section), seul le libellé ne le montrait pas avant le retour utilisateur.
- **Rangs** (`RowsScreen`, plein écran, retour utilisateur après test réel) : un bloc `rows` s'ouvre sur un seul écran listant tous ses rangs, modifiables en place (côté END/ENV, instructions, mailles après) — plus de feuille par rang. Le numéro n'est **jamais** saisi à la main : c'est une pastille en lecture seule dérivée de la position du rang dans le tableau (`index + 1`), donc toujours juste, y compris tout de suite après un glisser-déposer — `row.number` reste dans le modèle de données (rempli à la création, lu par `parsePastedRows`) mais n'est plus affiché ni modifiable depuis cet écran. Chaque carte est bordée dans la couleur du côté (rose pour END, bleu pour ENV — une section "en rond" garde toujours le rose, faute de côté) plutôt qu'un simple liseré de couleur à gauche, espacée de ses voisines (`--space-16`, plus que le simple `gap` des autres listes de l'arbre — des cartes plus proches se lisaient comme un seul bloc), et le champ instructions n'a plus d'encart (juste un soulignement, `styles.textareaPlain` de `FormSheet.module.css`) pour rester court — placeholder "Instructions…". Chaque rang a des icônes dupliquer/supprimer directes sur sa carte (pas de menu "⋯" pour un rang ; le menu "⋯" reste pour pièce/section/bloc). "+ Ajouter un rang" insère directement une carte éditable avec le côté alterné prérempli (uniquement en section à plat) — pas de sous-formulaire. "Coller plusieurs rangs" (`PasteRowsSheet`, feuille du bas superposée à l'écran Rangs) affiche un aperçu en direct des rangs détectés par `parsePastedRows`, modifiable (on édite le texte collé, ou on retire une ligne individuellement) avant de valider.
- **Enregistrement automatique** (`useGuideAutosave`) : écriture différée de 400 ms après chaque modification, plus écriture immédiate sur `visibilitychange` (hidden), `pagehide` et à la sortie de l'éditeur ; toujours le contenu entier. `lastEditedNodeId` est mis à jour à chaque modification et sert, à la réouverture, à déplier automatiquement le chemin vers ce nœud (`computeAncestorIds`) — le reste démarre plié.
- **Annuler/Rétablir** (`useGuideHistory`) : historique en mémoire de 30 états maximum, jamais persisté ; une suppression affiche un message temporaire "[Nœud] supprimé, Annuler" qui rejoue le même mécanisme.
- **Fiche projet, carte "Guide de patron"** (`ProjectGuideCard`, remplace la carte grisée) : guides liés (nom, nombre de rangs, ouvrir, retirer), "Associer un guide" (recherche dans la bibliothèque) et "Créer un guide" (préremplit le type du projet et son premier patron lié, puis lie automatiquement le guide créé au projet). **Fiche d'un patron** : section "Guides" listant les guides qui le référencent, avec "Créer un guide pour ce patron" (préremplit `patternId`). Le bouton "Continuer" de la fiche projet ouvre le guide associé en priorité (avant la vue de travail patron/compteur) dès qu'un guide est lié — voir "Décisions d'interface (étape 1)". Depuis l'étape 5b, cette carte affiche aussi la progression de chaque guide et "Continuer" ouvre directement l'écran de suivi plutôt que l'éditeur — voir "Décisions d'interface (étape 5b)".
- **Volet patron dans l'éditeur** : si le guide a un patron lié, un sélecteur en pilule "Guide | Patron" apparaît sous l'en-tête ; les deux vues restent montées en permanence (comme le sélecteur Patron/Compteur de la vue de travail) pour que la position du PDF et l'état de l'éditeur survivent à un aller-retour. Sur iPad/écran large en paysage (≥ 1024px), les pilules se masquent au profit d'un partage côte à côte (~55 % éditeur / 45 % patron). Réutilise `PdfViewerCore` tel quel, avec `projectId: null` (position de lecture liée au patron seul, pas à un projet) — même composant que le bouton d'accès rapide au patron des panneaux d'édition ci-dessus.
- **Route de retour** : l'éditeur lit `location.state.returnTo` (repli sur `/patrons`) pour que le bouton retour, la suppression et la création depuis un projet/un patron ramènent exactement là d'où le guide a été ouvert — même convention que la visionneuse PDF de l'étape 4.

## Modèle de données (étape 5b — progression des guides)

- Schéma Dexie en version 13 (`src/data/db.ts`) : v12 ajoute `guideProgress` (`id, projectId, guideId, [projectId+guideId]`, un seul enregistrement par couple projet/guide) ; v13 ajoute `settings.guideRowTextSize` (défaut `'medium'`, backfillé sur les installs existantes).
- `guideProgress` (`GuideProgressRecord`, `src/data/types.ts`) : projectId, guideId, activePieceId (nullable — la pièce en cours, toujours celle que `getNextAvailablePieceId` autorise, jamais un choix libre), pieces (`Record<pieceId, PieceProgress>`), linkedCounterId (nullable, voir "Compteur intégré" plus bas), startedAt, lastAdvancedAt, completedAt (nullable, posé quand toutes les pièces sont "done"). `PieceProgress` : status (`todo | in_progress | done`), cursor (`Cursor | null`), history (jusqu'à `PIECE_HISTORY_LIMIT` = 100 curseurs passés, le plus récent en dernier — comment `back` annule un pas sans le recalculer structurellement), stepsDone (recalculé de zéro à chaque action, jamais accumulé).
- **La progression ne va jamais dans l'arbre** (règle posée à l'étape 5a, tenue ici) : `guideProgress` est une table à part, indexée par `[projectId+guideId]`, jamais par id de nœud — un même guide (`guideContents`) reste un modèle partageable par plusieurs projets, chacun avec sa propre progression.
- **Principe : les pièces se tricotent toujours dans l'ordre du tableau `pieces`, jamais en parallèle ni hors ordre.** `getNextAvailablePieceId` (`src/data/guideProgress.ts`) renvoie la première pièce non "done" dans l'ordre du tableau ; `setActivePiece` et l'action `goTo` d'`advanceGuide` refusent toute pièce qui n'est pas exactement celle-là (sauf pour relire une pièce déjà "done", voir plus bas — la seule exception à "dans l'ordre"). Recommencer une pièce (`resetProgress`) efface donc aussi la progression de toutes les pièces qui la suivent dans le tableau, pour ne jamais laisser une pièce "done" après une pièce redevenue "todo".
- **Cursor** (`src/data/guideProgress.ts`) : position exacte dans une seule pièce (jamais à cheval sur deux pièces) — `{ nodeId, step, blockId, passages }`. `step` distingue les cinq natures de position (`operation` = montage/finition, `row`, `text`, `single` = bloc mesure/nombre de mailles sans enfant, `checkpoint` = le bloc mesure/nombre de mailles lui-même, à son point de décision "Longueur/mailles atteint ?"). `blockId` ne sert que pour un `row` (le bloc `rows` contenant, utilisé par `repairCursor` pour retomber sur un autre rang du même bloc). `passages` est une map `{ [idDuBlocRépétition/mesure/nombreDeMailles]: numéroDePassage }` de tous les blocs à répétition ancestraux de la position — toujours reconstruite de zéro par chaque fonction, jamais lue telle quelle, pour ne jamais garder une entrée périmée.
- **Parcours d'une pièce** : montage (si présent) → blocs de chaque section dans l'ordre → finition (si présente). Un bloc `rows` linéarise chacun de ses rangs ; un bloc `text` est un seul pas ; un bloc `repeat(N fois)` boucle automatiquement sur ses N passages puis se comporte comme un pas terminé une fois épuisé ; un bloc `measure`/`stitch_count` ne boucle **jamais** automatiquement — la fin de chaque passage de ses enfants ouvre systématiquement un `checkpoint` ("Oui, continuer" / "Pas encore, refaire un passage" / "Terminer ce bloc maintenant"). Un bloc vide, ou un bloc `rows` sans rang, ne produit aucun pas (rien à traverser).
- **Avancer/reculer** : `advance` est le seul point d'entrée pour avancer (pas suivant normal, résolution d'un checkpoint via `options.reached`, ou `options.finishBlock` pour sortir immédiatement du bloc mesure/nombre de mailles ancestral le plus proche quel que soit l'avancement du passage en cours). `back` dépile `history` en priorité (le curseur exact précédent) et ne recalcule structurellement que si l'historique est vide, ce qui n'est pas toujours possible : reculer par-delà un bloc mesure/nombre de mailles déjà entièrement passé ne peut pas retrouver combien de passages il a réellement pris — `back` reste alors immobile plutôt que de deviner.
- **goTo** (utilisé par le Plan du guide) : place le curseur directement sur un nœud cible sans reparcourir ce qu'il y a entre les deux ; tous les blocs ancestraux autres que celui contenant directement la cible repartent au passage 1 ; celui-là garde le passage du curseur courant s'il y était déjà, sinon 1 (`GoToOptions.loopPassage` pour choisir explicitement). Un `goTo` vers une pièce autre que l'active n'est autorisé que si cette pièce est déjà "done" — c'est la seule action qui peut cibler une pièce autre que l'active, pour la relire/corriger sans jamais la rouvrir ni toucher le compteur lié.
- **repairCursor** : repositionnement au mieux après une édition du guide sous les pieds du curseur (typo, suppression du rang courant, etc.), essayé dans l'ordre : (1) le bloc `rows` du rang supprimé existe encore et a encore au moins un rang → premier rang restant de ce bloc ; (2) le conteneur ancêtre (répétition/mesure/nombre de mailles) le plus proche qui existe encore → son premier pas restant ; (3) tout début de la pièce. Appelé automatiquement (`repairActiveCursor`) après chaque modification du guide via "Corriger" depuis l'écran de suivi ; un message "Le guide a changé, ta position a été ajustée." s'affiche 4 secondes si le curseur a réellement dû bouger.
- **Décompte des pas** (`countSteps`, `computeStepsDone`, `getPieceProgress`, `getGuideProgress`) : un pas de longueur variable (mesure/nombre de mailles) ne compte qu'un seul passage dans le total "connu" — les passages supplémentaires réellement faits s'ajoutent à `stepsDone` sans jamais faire dépasser 100 % à une pièce ou au guide entier (`Math.min(100, …)`).
- **`computeProjectProgress`** (`src/data/progress.ts`) : signature étendue avec un second paramètre optionnel `guides: ProgressGuideInput[] = []` (rétrocompatible avec tout appelant d'avant l'étape 5b) — dès qu'au moins un guide lié au projet a un total de pas connu non nul, la progression du projet devient la somme pas faits/pas connus de **tous** ses guides liés (prioritaire sur le calcul par compteurs) ; sinon, comportement inchangé depuis l'étape 1 (compteur principal, sinon moyenne des compteurs à objectif, sinon nombre de rangs). `getProjectGuideProgressInputs(projectId)` (`guideProgressRepository.ts`) construit ce tableau depuis la base.
- **API transactionnelle** (`src/data/guideProgressRepository.ts`, jamais Dexie dans les composants) : `getOrCreateProgress`, `setActivePiece` (refuse toute pièce hors ordre), `startGuide` (crée la progression si besoin, saute automatiquement toute pièce à zéro pas en la marquant "done" directement plutôt que d'y rester bloqué, positionne `activePieceId` via `getNextAvailablePieceId`, démarre une session `origin: 'guide'`), `advanceGuide` (**une seule transaction Dexie** par action — relit progression et contenu du guide à jour, répare le curseur si besoin, calcule le nouveau curseur/statut/`stepsDone`, répercute next/back sur le compteur lié le cas échéant via `applyCounterDeltaInTx`, la même fonction transactionnelle qu'un appui sur le compteur à l'étape 1, met à jour `lastActivityAt` du projet et appelle `recordActivity` avec `origin: 'guide'`), `resetProgress` (guide entier ou une pièce, cascade vers les pièces suivantes, ne touche jamais aux sessions ni au compteur lié), `setLinkedCounter`, `repairActiveCursor` (le seul appel de `repairCursor` qui écrit en base, sans aucun effet de bord session/compteur), `getProjectGuideProgressInputs`, `getProjectResumeSummary(projectId)` (résumé de reprise pour l'étape 6 : pièce/description/pourcentage du guide lié le plus récemment avancé et non terminé, `null` si aucune progression enregistrée pour ce projet).
- **Cascades** : supprimer un guide (`deleteGuide`) ou un projet (`deleteProject`) supprime aussi son/ses `guideProgress` ; retirer le lien projet-guide (`unlinkGuideFromProject`, avec confirmation explicite côté UI précisant l'effet) supprime également la progression associée.

## Décisions d'interface (étape 5b)

- **Point d'entrée "Suivre dans un projet"** (`useFollowGuideFlow`, depuis le menu de l'éditeur et depuis `GuidesLibraryView`) : navigation directe si le guide n'est lié qu'à un seul projet ; sinon feuille `FollowGuideSheet` — recherche + liste de tous les projets, avec liaison automatique du projet choisi si le guide n'est encore lié à aucun ("pickAny"), ou recherche parmi les seuls projets déjà liés s'il y en a plusieurs ("pickLinked").
- **Écran de départ** (`GuideStartScreen`, via `GuidePanel`) : toujours affiché en premier à l'ouverture de `/#/projets/:id/guides/:id/suivre`, que le guide soit vierge ou déjà en cours — ouvrir cet écran, ou modifier le guide entre-temps, ne démarre jamais le chrono ; seul l'appui sur "Commencer"/"Reprendre" (`startGuide`) le fait. Liste des pièces avec leur état (verrouillée/à faire/en cours/fait, nombre de pas ou "Aucun pas"), résumé de reprise (`getResumeSummary`) si une progression existe, bouton unique dont le libellé s'adapte ("Commencer" / "Reprendre" / "Voir le résultat" une fois le guide entièrement terminé).
- **Écran de suivi** (`GuideFollowScreen`) : en-tête minimal (retour, nom du guide, menu "⋯"). En dessous, `GuideProgressHeader` (nom de la pièce, section, barre de progression + pourcentage **de la pièce entière**, jamais de la section/du bloc courant, pour rester cohérent avec le Plan du guide et la fiche projet) et, à côté du pourcentage, le **même** `ChronoButton` (extrait de `CounterPanel` en composant partagé, `src/components/counters/ChronoButton.tsx`) que l'écran compteur. Puis `StepCards` : une carte "Rang" (position **locale** au sein de son propre bloc `rows`, ex. "3 / 13" — distincte du numéro de rang du patron, voir `CursorDescription.rowIndexInBlock`) colorée par côté (framboise = END, bleu = ENV, même convention que `RowsScreen` de l'étape 5a) et, si le pas est dans une répétition/mesure/nombre de mailles, une seconde carte "Répétition"/"Passage" réutilisant directement la couleur et l'icône du type de bloc (`blockTypeMeta`, étape 5a) — aucune couleur/icône dédiée à réinventer. Carte d'instruction volontairement épurée (texte du pas, rien d'autre) et aperçu du pas suivant ("Ensuite : …"). Décisions détaillées dans "Refonte visuelle" ci-dessous.
- **Point de contrôle** (`CheckpointScreen`) : écran dédié plutôt qu'une simple carte parmi d'autres pour la question "Longueur/nombre de mailles atteint ?" d'un bloc mesure/nombre de mailles, avec ses trois issues (continuer, refaire un passage, terminer le bloc maintenant).
- **Fin de pièce / fin de guide** : `PieceFinishedScreen` ("Passer à [pièce suivante]", jamais automatique — un bouton "Retour" en plus seulement quand l'écran a son propre retour, voir Vue de travail) et `GuideFinishedScreen` (félicitations sobres, "Marquer le projet comme terminé" via les mêmes règles de statut/date que le formulaire projet — jamais automatique — et "Recommencer").
- **Plan du guide** (`GuidePlanSheet`) : arbre pièce > section (repliable) > rangs à plat, statut et pourcentage (`getNodeStatus`) à chaque niveau (jamais à l'intérieur d'une répétition, qui reste un simple sous-total). "Aller ici" (`goTo`) uniquement sur un rang de la pièce active ou d'une pièce déjà "done" (rang désactivé + note "Termine d'abord…" sinon), avec confirmation explicite avant le saut. "Recommencer cette pièce"/"Recommencer le guide", chacun avec confirmation rappelant que le temps passé et les compteurs ne sont pas remis à zéro.
- **Corriger** (`CorrectStepSheet`) : rouvre l'écran/la feuille d'édition exacte de l'éditeur de l'étape 5a pour le nœud du pas courant (`RowsScreen` pour un rang — sans les actions "Ajouter"/"Coller", qui n'ont pas de sens ici —, `TextBlockSheet`, `OperationSheet`, `MeasureSheet`/`StitchCountSheet`), écrit via les mêmes fonctions pures que l'éditeur (`updateNode`/`deleteNode`/`moveNode`/`duplicateNode`/`setOperation`), puis appelle `repairActiveCursor` en sortie et affiche le message "ajustée" si la position a dû bouger.
- **Compteur intégré** (`LinkedCounterSheet`, optionnel, menu "⋯") : associe un compteur du projet à ce guide (`linkedCounterId`) — chaque "Rang suivant"/"Précédent" validé sur un pas de type rang lui applique +1/-1 (jamais en dessous de 0, via `applyCounterDeltaInTx`), en plus du décompte propre du guide qui reste affiché sur l'écran de suivi ; un pas qui n'est pas un rang (texte, montage/finition, checkpoint) ne touche jamais le compteur lié.
- **Réglages, section "Guide"** : sélecteur à 4 tailles de texte (`guideRowTextSize`, petit/moyen/grand/très grand) avec aperçu en direct, pour le texte des rangs sur l'écran de suivi uniquement.
- **Historique des sessions** (`SessionHistorySheet`) : une pill "Guide" distingue désormais une session `origin: 'guide'` des sessions `'counter'`/`'manual'`.
- **Vue de travail** (`ProjectWorkPage`) : l'onglet "Guide" n'est plus désactivé — pilule à 3 branches "Patron | Guide | Compteur" sur téléphone, les trois panneaux (patron, `GuidePanel`, `CounterPanel`) restent montés en permanence (`display: none`, jamais démonté) pour que chacun garde sa position. Sur iPad/écran large en paysage (≥ 1024px), le panneau patron reste toujours visible à gauche (~50 %) et une pilule interne "Guide | Compteur" (masquée sur téléphone) bascule la colonne de droite — un `useMediaQuery` JS (`src/hooks/useMediaQuery.ts`) reproduit ici la media query CSS, seul endroit de l'app où un simple `display: none`/`flex` par CSS ne suffisait pas à décider quel panneau afficher. Plusieurs guides liés → sélecteur discret au-dessus du panneau, guide le plus récemment avancé mémorisé (`useLastUsedGuideId`, basé sur `guideProgress.lastAdvancedAt`, jamais un champ dédié). Le bouton "Continuer" de la fiche projet ouvre désormais directement l'écran de suivi (`/guides/:id/suivre`) du guide le plus récemment avancé (ou le premier lié) dès qu'un guide est associé — l'éditeur reste accessible depuis la carte "Guide de patron" et la bibliothèque.
- **Fiche projet, carte "Guide de patron"** (`ProjectGuideCard`) : chaque guide lié affiche désormais `X % · [pièce] · [pas]` une fois commencé (sinon le nombre de rangs comme avant), et un bouton "Reprendre" vers l'écran de suivi ; retirer un guide affiche une confirmation explicite précisant que sa progression sera supprimée.
- **Fiche d'un guide / bibliothèque** (`GuideCard`) : bouton "Suivre" (icône lecture) en plus d'ouvrir l'éditeur ; pourcentage affiché quand le guide n'est lié qu'à un seul projet (`useGuideProjectsProgress`).
- **Chargement différé** : l'écran de suivi (`GuideFollowPage`/`GuidePanel` et tout `src/components/guides/follow/`) est chargé en import dynamique (`LazyGuideFollowPage`, `LazyGuidePanel`) — indispensable car "Corriger" réutilise les feuilles d'édition de l'éditeur de l'étape 5a, qui dépendent de `@dnd-kit` : sans ce découpage, `ProjectWorkPage` (qui n'est lui-même pas chargé en différé) aurait tiré `@dnd-kit` dans le bundle principal dès qu'un projet a un guide lié. Vérifié après coup sur le build (`dist/index.html`, contenu des chunks) : aucun symbole `@dnd-kit`/pdf.js dans les chunks préchargés au démarrage.

### Refonte visuelle de l'écran de suivi (retour utilisateur)

Retour explicite de l'utilisateur après un premier essai de l'étape 5b : reprendre la **structure** d'une app de tricot existante (jamais son visuel — palette, typographie et composants restent ceux de Tricot), avec le compteur lié et l'espace "Note"/photo en moins, et l'accès au patron en plus. Composants partagés entre l'écran de suivi et l'aperçu (voir plus bas), tous dans `src/components/guides/follow/` :

- **`GuideProgressHeader`** (nom de pièce + section + barre de progression pleine largeur + pourcentage) : un composant simple à part plutôt qu'une réutilisation de `StripedProgressBar` — celle-ci porte la métaphore rayée du stock de laine/des compteurs, hors de propos ici.
- **`StepCards`** (les cartes "Rang"/"Répétition"/"Passage") : `CursorDescription` (`src/data/guideProgress.ts`) porte désormais `rowIndexInBlock`/`rowCountInBlock` (position du rang dans son propre bloc `rows`, jamais son `row.number`) et `innermostContainer` (le bloc répétition/mesure/nombre de mailles le plus proche, avec son passage courant et, pour une répétition seulement, son total — une mesure/un nombre de mailles n'a jamais de total connu à l'avance). Ces champs sont calculés par `describeCursor`, jamais recalculés dans l'UI.
- **`StepOverviewCard`** ("Aperçu du bloc", repliée par défaut) : liste plate des rangs/blocs du bloc répétition/mesure/nombre de mailles **courant seulement** (pas toute la pièce), rang actif en surbrillance — **purement informative, aucune navigation au tap** (décision explicite : le Plan du guide reste le seul endroit pour sauter quelque part). `getContainerStepOverview` (`guideProgress.ts`) en calcule le contenu ; un conteneur imbriqué à l'intérieur n'est jamais déroulé, juste résumé sur une ligne.
- **Corriger / Terminer ce bloc maintenant** : déplacés de la carte d'instruction vers le menu "⋯" (`GuideFollowMenuSheet`) pour que cette carte reste aussi sobre que le texte du pas lui-même ; "Terminer ce bloc" n'apparaît dans le menu que quand il s'applique (dans un bloc mesure/nombre de mailles), comme avant.
- **Voir le patron** : nouveau bouton (icône livre) sous la carte, visible seulement si le guide a un patron lié, ouvrant `PdfViewerCore` en plein écran par-dessus l'écran de suivi (même mécanisme que le bouton dédié de l'éditeur, `FullScreenPanel`) — fermeture ramène exactement à l'écran de suivi, jamais démonté entre-temps. `GuidePanel` résout ce patron lié via `usePattern(guide.patternId)`.

### Aperçu du guide (lecture seule, sans projet)

Un guide peut se parcourir à blanc, sans l'associer à un projet ni compter la moindre avancée — utile pour relire un guide qu'on vient d'écrire. Point d'entrée unique : menu "⋯" de l'éditeur (`GuideMenuSheet`) → "Aperçu", route dédiée `/#/guides/:guideId/apercu` (`GuidePreviewPage`/`LazyGuidePreviewPage`, chargée en différé comme le reste de `follow/`).

- **`GuidePreviewScreen`** : réutilise les mêmes `GuideProgressHeader`/`StepCards`/`StepOverviewCard`/carte d'instruction que l'écran de suivi réel, avec une pill "Aperçu — lecture seule" toujours visible. Position (`Cursor`) tenue en **state React local, jamais dans `guideProgress`** — aucune session, aucun chrono, aucun compteur lié : c'est la différence fondamentale avec `/suivre`.
- **Navigation libre entre pièces** : un sélecteur en pilules (une par pièce) permet de sauter n'importe où, y compris une pièce qui serait "verrouillée" en vrai suivi — rien n'est réellement tricoté, donc aucune notion d'ordre à faire respecter. Choisir une pièce réinitialise le curseur à son premier pas (`getInitialCursor`) et l'historique local.
- **Avancer/reculer** réutilisent exactement `advance`/`back` (`guideProgress.ts`), donc le même comportement pour répétitions/mesures/nombre de mailles/checkpoints que le suivi réel. Terminer une pièce passe automatiquement à la suivante (pas d'écran "Pièce terminée" : rien à célébrer en lecture seule) ; terminer la dernière affiche une note "Fin de l'aperçu" avec "Recommencer l'aperçu" (revient à la première pièce ayant au moins un pas).
- **Jamais de "Corriger"** ni de Plan du guide ici : éditer le contenu reste le rôle de l'éditeur, pas de l'aperçu.

## Sauvegarde et restauration (étape 7)

Schéma Dexie en version 14 (`src/data/db.ts`) : v14 ajoute `settings.lastBackupAt` (nullable), `backupReminderEnabled` (défaut `true`), `backupReminderIntervalDays` (`7 | 14 | 30 | null`, défaut 14, `null` = jamais) et `backupReminderSnoozedAt`. Les déclarations de version vivent maintenant dans `declareSchema(db, upToVersion)` (même contenu qu'avant, aucune version publiée modifiée) ; `CURRENT_SCHEMA_VERSION` (= 14, à incrémenter avec chaque nouvelle version, un test vérifie qu'il égale `db.verno`) est la version écrite dans les sauvegardes.

Tout le code non-UI est dans `src/data/backup/` (exporté par `src/data/index.ts`) ; l'UI dans `src/components/backup/` (`BackupSection` des Réglages, `BackupExportSheet`, `ImportBackupSheet`, `BackupReminderBanner` de l'Accueil) et `src/hooks/useBackupExport.ts`/`useBackupReminder.ts`.

**Limite honnête (PWA iOS) : Safari n'autorise aucune écriture de fichier sans geste de l'utilisateur.** La "sauvegarde automatique" signifie : contenu généré automatiquement + rappel automatique + export réduit à un seul geste (confirmation de la feuille de partage ou de l'enregistrement). Ne jamais écrire dans l'interface "sauvegardé automatiquement en arrière-plan". Si la génération est longue, iOS peut juger le geste expiré (`NotAllowedError`) : la feuille propose alors un second appui explicite "Enregistrer / partager". `lastBackupAt` n'est écrit qu'une fois le fichier réellement remis (partage terminé, téléchargement déclenché, ou écrit dans le dossier choisi) — jamais si l'utilisateur ferme le partage.

**Format du fichier** `tricot-sauvegarde-AAAA-MM-JJ-HHhMM.zip` (préfixe `BACKUP_FILE_PREFIX`, dérivé de `APP_NAME`, heure locale) :
- `manifest.json` : `{ format: 1, schemaVersion, appVersion, exportedAt, counts }` (`counts` = nombre d'enregistrements par table, vérifié à l'import pour détecter une archive tronquée).
- `data.json` : une clé par table, tableaux bruts — `settings`, `projects`, `counters`, `counterEvents`, `coverImages`, `sessions`, `yarns`, `yarnImages`, `projectYarns`, `yarnUsages`, `patterns`, `patternFiles`, `patternCovers`, `projectPatterns`, `patternViewStates`, `guides`, `guideContents`, `projectGuides`, `guideProgress` (`BACKUP_TABLES`). Les tables à blob (`coverImages`, `yarnImages`, `patternFiles`, `patternCovers`) gardent leurs métadonnées sans `blob`, plus `blobFile` (chemin dans le zip) et `blobType` (MIME, rétabli sur le Blob à l'import).
- `files/<table>/<id>.<ext>` : les blobs (`jpg`, `pdf`…, extension déduite du MIME), stockés sans compression (déjà compressés) ; `manifest.json`/`data.json` en DEFLATE. Zip généré en flux (`generateInternalStream`, `streamFiles: false` pour que Archive Utility de macOS l'ouvre) depuis un seul instantané de lecture Dexie ; JSZip n'est chargé qu'à la demande.

**Exclusion des secrets** : `getBackupExcludedSettingsKeys()` (`src/data/backup/secrets.ts`) liste les champs de réglages jamais exportés (`ravelryUsername`, `ravelryPassword`). Elle est utilisée par l'export ET, par précaution, par l'import (une archive bricolée qui en contiendrait est nettoyée). **Toute donnée sensible future ajoutée à `AppSettingsRecord` (clé d'API, jeton, mot de passe, identifiant) doit être ajoutée à cette liste** : `backup.test.ts` échoue si un champ de réglage au nom sensible (`password`, `secret`, `token`, `apiKey`, `username`, `credential`…) n'y figure pas, et si une valeur secrète apparaît n'importe où dans l'archive.

**Import** (`openBackup`, aucune écriture avant validation) : manifeste valide, `schemaVersion` plus récente que `CURRENT_SCHEMA_VERSION` → refus ("Cette sauvegarde vient d'une version plus récente de l'app, mets-la à jour avant d'importer"), `data.json` valide, ids uniques, `counts` cohérents, tous les fichiers référencés présents. **Sauvegarde plus ancienne** : ses lignes sont insérées dans une base Dexie temporaire déclarée à l'ancienne version (`declareSchema(temp, schemaVersion)`) puis rouverte à la version courante, donc les `.upgrade()` existants s'exécutent tels quels — aucune migration dupliquée (`migrateTablesToCurrent`). Les blobs ne participent pas à la migration (aucun `.upgrade()` ne les touche) et sont rattachés après. Les contenus de guides passent par `migrateGuideContent`. Les tables inconnues à cette version sont ignorées.

**Remplacer tout** (`restoreReplaceAll`) : tous les fichiers sont d'abord lus en mémoire, puis la base est vidée et remplie dans **une seule transaction** — un échec (dont `QuotaExceededError`) laisse les données actuelles intactes. Les identifiants Ravelry de l'appareil sont conservés (ils ne sont jamais dans une sauvegarde, les effacer n'apporterait rien) ; `lastBackupAt` prend la date de la sauvegarde restaurée. Confirmation forte avec le nombre d'enregistrements perdus (sauf base vide). Proposé par défaut si la base n'a ni projet, ni patron, ni fil, ni guide ; sinon "Fusionner" est proposé en premier.

**Fusionner** (`restoreMerge`) — règle exacte, jamais d'écrasement : (1) une ligne dont l'id existe déjà est conservée telle quelle et comptée comme ignorée ; (2) les lignes "possédées" suivent leur parent : compteurs/couverture d'un projet, événements d'un compteur, photo d'un fil, fichier/couverture d'un patron, contenu d'un guide sont ignorés si le parent existe déjà (évite deux compteurs principaux ou des `sequence` en collision) ; (3) les liens à un seul exemplaire par paire (`projectYarns`, `projectPatterns`, `projectGuides`, `guideProgress`, `patternViewStates`) sont ignorés si la paire existe déjà sous un autre id ; (4) une ligne qui pointe vers un parent introuvable partout est sautée avec un avertissement ; (5) les réglages ne sont jamais modifiés. Une transaction Dexie par famille (fils ; patrons ; guides ; projets+compteurs+événements+photos+sessions ; liens), parents d'abord : une erreur laisse le groupe en cours intact, les groupes précédents importés, et le message dit lequel. Des patrons identiques (même `fileHash`) sous des ids différents sont tous deux conservés, comme à l'import normal.

Après toute restauration : `navigator.storage.persist()` est redemandé s'il n'est pas actif, et le résumé rappelle de ressaisir les identifiants Ravelry si la recherche était activée dans la sauvegarde.

**Rappel** (`getBackupReminderState`, fonction pure testée) : actif si `backupReminderEnabled`, intervalle non nul, au moins un projet ou un fil, et un intervalle entier écoulé depuis le plus récent de `lastBackupAt` et `backupReminderSnoozedAt` (jamais sauvegardé = dû). Décidé une seule fois par session de l'app (`decideReminderForSession`, premier rendu de l'Accueil) : "Plus tard" repousse d'un intervalle complet (`backupReminderSnoozedAt`), "Fermer" ne masque que pour la session.

**Dossier persistant** (`backupFolder.ts`, optionnel, jamais indispensable) : proposé seulement si `window.showDirectoryPicker` existe (File System Access API ; absent de Safari iOS, l'option n'est alors pas rendue du tout). Le `FileSystemDirectoryHandle` est stocké dans une base IndexedDB séparée (`tricot-backup-folder`), hors schéma Dexie et hors de toute sauvegarde. La permission est redemandée au tap, avant la génération (les navigateurs n'affichent le prompt que sur un geste frais) ; si elle est refusée, la sauvegarde retombe sur le partage/téléchargement avec un message clair. Les anciennes sauvegardes du dossier ne sont jamais supprimées.

Interface : section "Sauvegarde" des Réglages (sous "Catalogue Ravelry") — dernière sauvegarde en relatif, "Exporter mes données", "Importer une sauvegarde" (sélecteur de fichier, glisser-déposer sur ordinateur/iPad), rappel (interrupteur + 7/14/30 jours/jamais), dossier persistant si disponible ; bandeau discret en haut de l'Accueil.

Mémoire : l'export et l'import tiennent le zip en mémoire (JSZip) ; « Remplacer tout » charge en plus tous les fichiers avant d'écrire. Usage normal visé : dizaines à quelques centaines de Mo.

## Fiabilité du compteur

- Chaque +1/-1/+5/remise à zéro/valeur manuelle/annulation passe par une seule transaction Dexie (`src/data/countersRepository.ts`) qui lit la valeur courante dans la transaction (jamais depuis l'état React), met à jour le compteur, ajoute l'événement et touche `lastActivityAt` du projet. Les transactions Dexie sur les mêmes tables sont sérialisées par IndexedDB : des appuis en rafale ne perdent jamais de comptage (testé avec 30 appels concurrents dans `countersRepository.test.ts`).
- Les événements sont ordonnés par `sequence` (entier croissant calculé dans la même transaction que l'écriture), jamais par `createdAt` seul : deux appuis assez rapides pour tomber dans la même milliseconde donneraient sinon un ordre indéterminé, et l'annulation répétée pourrait restaurer la mauvaise valeur.
- L'annulation restaure `valueBefore` du dernier événement non annulé et le marque `undoneAt` ; répétable indéfiniment, pas de "rétablir" pour l'instant.
- Écran allumé via l'API Wake Lock (`useWakeLock`), avec repli silencieux si indisponible, refusée, ou en cas d'échec (à confirmer sur iOS réel).

## Suivi du temps (étape 2)

Le temps est mesuré par des sessions (`sessions`, schéma Dexie v6 dans `src/data/db.ts`) : id, createdAt, updatedAt, projectId (`null` = compteur autonome, même scan complet que `counters` pour ce cas), startedAt, endedAt (nullable), lastHeartbeatAt, source (`auto` | `manual`), origin (`counter` | `guide` | `manual`), endReason (nullable : `user_stop` | `app_hidden` | `switched` | `recovered`). Réglage `settings.trackingEnabled` (défaut `true`) désactive tout nouvel enregistrement sans toucher aux sessions déjà enregistrées.

Règles de session :
- Une session démarre automatiquement au premier appui qui modifie un compteur (+1/-1/+5/remise à zéro/valeur manuelle/annulation — l'annulation compte comme une activité comme les autres), qu'il s'agisse d'un compteur de projet ou du compteur autonome. Ouvrir un écran sans appuyer ne démarre rien.
- Une seule session ouverte à la fois dans toute l'app. Un appui sur un compteur d'une autre cible (autre projet, ou projet vs compteur autonome) clôt la session en cours (`endReason: 'switched'`) et en ouvre une nouvelle, sans chevauchement. Un appui sur un autre compteur du même projet continue la session en cours.
- La session s'arrête quand l'app quitte le premier plan (`visibilitychange` → hidden, et `pagehide`, `endReason: 'app_hidden'`) ou par le bouton de chrono (`endReason: 'user_stop'`). Après un arrêt manuel, les appuis sur des compteurs de la même cible ne redémarrent pas le chrono ; seul le bouton le relance (nouvelle session, `source: 'manual'`). Ce statut « arrêté à la main » vit uniquement en mémoire (`src/data/sessionTrackingState.ts`, jamais persisté) et est effacé quand l'app quitte le premier plan, quand le chrono est relancé, ou quand un compteur d'une autre cible est tapé.
- Attribution du temps : une session avec `projectId` non nul compte dans le temps de ce projet ; une session `projectId: null` (compteur autonome) n'est jamais comptée dans le temps d'un projet mais entre dans les statistiques globales (voir `computeGlobalTimeStats`).
- Fiabilité : `lastHeartbeatAt` est écrit toutes les 10 s pendant qu'une session est ouverte et l'app visible (et à chaque activité), uniquement pour permettre la récupération — jamais un délai d'inactivité. `closeOrphanSessions()` clôt toute session ouverte qui n'appartient pas au contexte courant (`endedAt = lastHeartbeatAt`, `endReason: 'recovered'`), appelée au lancement, au retour au premier plan et avant chaque écriture d'activité (perte max 10 s si l'app est tuée sans prévenir).

API (`src/data/sessionsRepository.ts`, jamais Dexie dans les composants) :
- `recordActivity(target, at, tx, options)` : appelée depuis la même transaction qu'un appui sur un compteur (`countersRepository.ts` passe désormais `db.sessions`/`db.settings` et le `tx` de la transaction) — garantit qu'une session correcte est ouverte selon les règles ci-dessus. Depuis l'étape 5b, `advanceGuide` (`src/data/guideProgressRepository.ts`) appelle `recordActivity` de la même façon avec `origin: 'guide'` et le `projectId` du projet en cours de suivi ; `startGuide` appelle `startSession({ projectId }, 'guide')`.
- `startSession(target, origin)` / `stopSession(reason)` : démarrage/arrêt manuels (bouton de chrono).
- `closeOrphanSessions()`, `handleForegroundLoss()`, `touchHeartbeat()` : cycle de vie, appelés depuis `useSessionTracking` (monté une fois dans `App.tsx`), pas depuis les écrans.
- `getOpenSession`, `getSessionsForTarget`, `getAllSessions`, `addManualSession`, `updateSessionTimes`, `deleteSession`, `validateSessionTimes` (pure : futur interdit, fin après début, pas de chevauchement avec une autre session tous targets confondus) pour l'historique des sessions.
- Fonctions pures dans `src/data/timeStats.ts` (isolées et testées comme `progress.ts`, réutilisables à l'étape 6) : `getSessionDuration` (fin effective = `now` pour la session live de ce contexte, `lastHeartbeatAt` sinon — jamais un chronomètre en mémoire), `computeProjectTimeStats`, `computeGlobalTimeStats`, `aggregateTimeByPeriod` (répartit une session à cheval sur minuit sur les jours concernés, semaine du lundi au dimanche, heure locale). Formatage français unique dans `src/utils/formatDuration.ts` (`"12 h 30"`, `"45 min"`, `"< 1 min"`).
- Suppression d'un projet : cascade sur ses sessions (`deleteProjectSessions`) ; les sessions du compteur autonome ne sont jamais supprimées par ça.

## Agrégation globale, accueil et statistiques (étape 6)

Aucune table ni version Dexie ajoutée (schéma en v13 à ce stade ; l'étape 7 a ajouté la v14) : l'étape 6 ne fait qu'assembler des données existantes.

**L'accueil et l'onglet Stats ne contiennent aucune logique de calcul propre** : les pages et composants (`HomePage`, `StatsPage`, `CompletedProjectsPage`, `ResumeCard`) ne font que formater et afficher ce que renvoient les fonctions ci-dessous, qui appellent elles-mêmes `computeProjectProgress`, `getProjectResumeSummary`, `computeProjectTimeStats`, `computeGlobalTimeStats`/`aggregateTimeByPeriod` et les fonctions de `yarnMath.ts`. Un chiffre de l'onglet Stats et celui de la fiche projet viennent donc du même calcul.

Fonctions ajoutées, par module :

- `src/data/timeStats.ts` (pures) : `TimePeriod` gagne `'year'` ; `bucketKeyOfDay` + un regroupement interne unique jour→semaine/mois/année partagé par `aggregateTimeByPeriod` et `countCompletedProjectsByPeriod` (aucune duplication du découpage des périodes) ; `countCompletedProjectsByPeriod(projects, period, range)` (projets terminés par `completedAt`) ; `listBucketKeys` (toutes les périodes d'une plage, pour afficher les périodes vides) ; `getStatsWindow(view, now, earliestMs)` (plage + granularité de chaque vue : semaine calendaire du lundi par jour, mois par jour, année par mois, "tout" depuis la première activité par mois puis par année au-delà de 24 mois) ; `computeGlobalTimeStatsInRange` (totaux **tronqués à la plage**, donc toujours égaux à la somme des barres du graphique ; le nombre de sessions est celui des sessions qui *commencent* dans la plage).
- `src/data/yarnMath.ts` (pure) : `computeYarnConsumptionStats(yarns, usages, range?)` — grammes, mètres, pelotes, fils utilisés, top 3 des fils (classés en pelotes, seule unité comparable entre fils). Passe par `amountToSkeins`/`fromSkeins`. `partial` vaut `true` quand un usage n'est pas convertible (fil sans poids ou métrage par pelote) : les totaux g/m sont alors un minimum, l'UI le signale.
- `src/data/yarnsRepository.ts` : `computeGlobalYarnStats(range?)` (enveloppe asynchrone, filtre sur `usedAt`).
- `src/data/guideProgressRepository.ts` : `getLastUsedGuideId(projectId)` — le guide le plus récemment avancé, sinon le premier lié ; le hook `useLastUsedGuideId` s'appuie dessus.
- `src/data/dashboardRepository.ts` (lecture seule, assemblage) : `computeGlobalDashboardStats(now)`, `getRecentSessions(limit, { projectId })` (`null` = compteur de rang, absent = tout ; nom du projet ou `STANDALONE_COUNTER_LABEL`), `getContinueTarget`, `getActiveProjectsSummary(now)` (projets "En cours" par dernière activité : progression, point de reprise guide ou compteur, temps, cible de reprise), `getHomeDashboard(now)` et `getStatsOverview(view, now)` (un seul accès par écran, branchés sur un unique `useLiveQuery`, donc mémorisés tant que la base ne change pas), `getCompletedProjectsHistory`.
- Règle de navigation partagée : `getContinueRoute(projectId, target)` (`src/components/projects/continueRoute.ts`) — guide lié → écran de suivi, sinon patron lié → vue de travail (qui rouvre le dernier onglet, `projects.lastWorkTab`), sinon compteur. Utilisée par le bouton "Continuer" de la fiche projet et par "Reprendre" de l'accueil : même comportement garanti.
- Composants partagés extraits de `TimeCard` : `SegmentedControl` et `BarHistogram` (`src/components/ui`), réutilisés par l'onglet Stats (`fit` = pas de défilement horizontal, une étiquette d'axe sur N). `formatBucketLabel`, `formatResumePoint` ("Dos · Rang 12", aussi utilisé par `ProjectGuideCard`), `formatTotalDuration` ("0 min" pour une période vide), `formatSkeins`, `getGreeting` dans `src/utils`. `PROJECT_STRIPE_CLASS` (`src/components/projects/stripeMeta.ts`) remplace la table dupliquée de `ProjectCard`.

Décisions d'interface :

- **Accueil** (`HomePage`) : salutation selon l'heure, section "Reprendre" (5 cartes `ResumeCard` maximum : couverture ou rayures, nom, point de reprise, barre de progression, pill de durée si le suivi du temps est actif, bouton "Reprendre" ; état vide avec lien vers l'onglet Projets), lien "Voir tous mes projets en cours" (vers `/projets?statut=in_progress`, que `ProjectsPage` lit pour son filtre initial) au-delà de 5, raccourci "Compteur de rang", "En un coup d'œil" (4 `StatTile` : tricoté cette semaine, projets en cours, terminés ce mois, pelotes ce mois), sessions récentes (4). Le libellé "Compteur de rang" (et non "Compteur libre") est celui déjà utilisé dans l'app. Aucun appel réseau, aucun chrono démarré.
- **Stats** (`StatsPage`) : `SegmentedControl` Semaine/Mois/Année/Tout ; carte Projets (par statut + nombre de patrons, guides, fils en stock, indépendants de la période) ; vue d'ensemble de la période ; histogramme du temps ; histogramme des projets terminés + lien vers `/stats/termines` (`CompletedProjectsPage` : projets terminés, du plus récent au plus ancien, avec leur temps total) ; carte laine (poids, métrage, fils utilisés, top 3). Grille à une colonne sur iPhone, deux à partir de 768px. Le temps est masqué si `trackingEnabled` est faux.
- Le temps global inclut le compteur de rang ; le temps d'un projet ne l'inclut jamais (voir "Attribution du temps") : l'onglet Stats et la fiche projet ne coïncident donc que pour la part "projets" (`time.projectsMs`).

## Import d'un guide (étape 9)

**Aucune IA intégrée et aucun appel réseau.** La conversion d'un patron PDF en JSON se fait par la personne, dans une conversation séparée avec l'assistant IA de son choix ; l'app ne fait qu'importer le résultat (fichier `.json` ou texte collé). Le système de crédits IA du cahier des charges (section 8) est abandonné. Aucune clé d'API, aucun `fetch`/`XMLHttpRequest`/URL dans le module : `guideImport.test.ts` échoue si l'un de ces fichiers en contient un (`guideImport.ts`, `GuideImportPage.tsx`, `GuidePreviewTree.tsx`, `ImportHelpSheet.tsx`). Tout fonctionne en mode avion.

- Logique pure dans `src/data/guideImport.ts` (`analyzeGuideImport` → `invalid` | `valid` | `repairable`, jamais d'exception) : limite 5 Mo (`MAX_GUIDE_IMPORT_BYTES`), retrait d'une clôture « ```json », `JSON.parse` protégé (ligne/colonne si le navigateur donne la position), `schemaVersion` plus récente refusée, plus ancienne mise à niveau (`normalizeGuideContent` puis `migrateGuideContent`), `validateGuideContent`, puis réparation **proposée** par `normalizeGuideContent` (l'UI ne l'applique qu'après « Appliquer les corrections », avec avertissement quand elle supprime du contenu). Indices facultatifs `name`/`craft`/`sizeLabel` à côté de `pieces`, jamais stockés dans le contenu.
- `createGuide` accepte un `content` facultatif : guide et contenu sont écrits dans la même transaction que la création manuelle.
- UI : route lazy `/#/guides/importer` (`GuideImportPage`, `src/components/guides/import/`) ; entrées « Importer un guide » (bibliothèque de guides, y compris l'état vide) et « Importer un guide pour ce patron » (fiche patron, préremplit `patternId`). Aperçu en lecture seule (`GuidePreviewTree`) : il partage les métadonnées de l'éditeur (`blockTypeMeta`, libellés de catégories/opérations, tokens `--color-guide-*`) mais pas ses composants, liés au glisser-déposer et à `@dnd-kit` qui doit rester hors du bundle principal. Après import : redirection vers l'éditeur.
- Aide intégrée : bouton « Comment ça marche ? » (`ImportHelpSheet`). Le format exact, les champs facultatifs et un exemple inventé sont dans `docs/Guidespatrons.md` (section 7 et section 10).
